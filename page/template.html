At a glance

Winnow is a Bitcoin-only wallet written in Lean 4: the wallet, its peer networking and the app’s model, update and view compile to C, and LeanNative’s generated Objective-C shell draws them with UIKit. It checks the chain on the phone with compact block filters from Bitcoin peers it finds itself, and reaches Tor and I2P through gateways you run, with no client of its own.

Each wallet below holds its own keys on the phone, with the exceptions noted in the fourth column. Four of them (Phoenix, Bitkit, Blixt and Zeus) are Lightning-first wallets with an on-chain side; this page looks only at their Bitcoin wallet. The table shows defaults; most of these wallets let you change the chain source.

Code size

Winnow counts {{W_L}} lines of code: {{W_APP}} for the app and {{W_BTC}} for its own Bitcoin library, which lives in the same repository and includes {{W_PROOF_LINES}} lines of proofs. The other wallets count {{LR_MIN}} to {{LR_MAX}} times as many lines. That is the app, plus a Bitcoin library of its own for Muun.

The count leaves out the engines each wallet is built on. Green, Phoenix, Bitkit, Blixt and Zeus embed gdk, lightning-kmp, LDK Node and LND; four of the five are Lightning nodes. Winnow is built on LeanNative, a {{W_ENGINE_L}}-line framework that runs a Lean app on iOS; it plays the part SwiftUI or React Native play for the others, which are not counted either. Each engine is shown in the table, not in the totals. BlueWallet takes its Bitcoin primitives from npm packages, which the dependency tables count.

Winnow’s lines are denser, at about {{W_CPL}} characters each against {{O_CPL_MIN}}–{{O_CPL_MAX}} for the others. Counted in characters, the gap is {{CR_MIN}} to {{CR_MAX}} times.

Complexity and CRAP

CRAP scores each function by its cyclomatic complexity (CC, the number of paths through it) and how much of it the tests run: CRAP = CC² × (1 − coverage)³ + CC. Coverage needs each project’s test suite run with instrumentation, so it is not measured here. Testing can only bring CRAP down to CC, so complexity alone sets a floor: a function above 12 scores above 12 however well it is tested, and one above 30 fails crap4j’s default threshold whatever its tests. Complexity is measured on each wallet’s counted code, not on embedded engines.

{{P12_W}}% of Winnow’s {{W_FUNCS}} functions are above 12, against {{P12_MIN}}–{{P12_MAX}}% for the others. Its mean is {{W_MEAN}}; the others’ range from {{MEAN_MIN}} to {{MEAN_MAX}}. Its most complex function, {{W_TOP}}, scores {{W_MAXCC}}: Winnow’s app follows the Elm architecture, and its update and command dispatchers are single match expressions with an arm for each message, which this rule counts as paths. {{W_GT30}} of its functions are above 30.

Machine-checked proofs

Lean is also a proof assistant, so part of Winnow’s code comes with theorems that Lean’s kernel checks on every build. Tests check examples; a theorem covers every input. The other wallets are written in languages without proofs, so this section has nothing to compare them on.

{{W_THM}}

Theorems in Winnow’s code

{{W_PROOF_LINES}} lines, all in its Bitcoin library’s secp256k1: limb and field arithmetic, the curve and its Jacobian formulas. {{GATE_LINK}} lists them, and the build fails if one rests on sorry or an extra axiom.

{{E_THM}}

Theorems in LeanNative

{{E_PROOF_LINES}} lines, most of them about how the runtime steps an app: each step runs update on one message and asks for exactly that message’s commands, whatever the order of events. The Objective-C renderer and platform effects are not proved; they are trusted and tested.

Not proved

What the theorems leave out

The wallet logic, networking and app have tests, not proofs. Signing runs on the proved arithmetic but is not constant-time: its timing depends on the key ({{SECP_LINK}}).

Proofs are erased when Lean compiles, so they add nothing to the app. They are counted as lines in the code size above, and are not functions in the complexity table.

Dependencies and vendored code

Winnow resolves no third-party package: its Lake manifest pins only LeanNative, the framework counted above as its engine. Like every Lean program it links Lean’s runtime and standard library from the toolchain, which bring libuv and GMP; they are under prebuilt binaries below. The others depend on {{DEP_MIN}} to {{DEP_MAX}} packages, counting what their embedded engines pull in, because that code ships in the app too. Package counts from different ecosystems are not equal units: an npm package is often a few hundred lines, a Rust crate or Go module often more. Read them per row.

What the numbers leave out

Less code is not proof of safety

A smaller codebase is quicker to read and review. It does not show the code is correct, and it says nothing about whether anyone independent has reviewed it. Check each project’s own security page.

The wallets do different amounts of work

Each count is the whole app, not only its on-chain wallet. Zeus also manages remote LND and Core Lightning nodes and includes Cashu, Nostr Wallet Connect and a point of sale. Bitkit includes Pubky contacts, Paykit and Trezor support. Winnow includes k-of-n multisig accounts and a Ledger signer. BlueWallet includes Lightning wallet types (an LNDHub custodian and an Ark one). Green’s count includes its lightning folder. Muun includes Lightning payments through swaps.

Engines are not counted

Phoenix, Bitkit, Blixt, Zeus and Green build their Bitcoin wallet on an engine that is a separate project: lightning-kmp, LDK Node with BDK, LND and gdk, so they look smaller than everything they ship. Winnow’s engine is a UI framework, LeanNative; its Bitcoin code is its own and counted, as Muun’s is. BlueWallet has no engine.

Who can move on-chain funds

Where a service has to cosign, the wallet cannot spend without it, or only after a delay. The fourth column of the table at the top says which wallets that applies to, and the notes under each cell give the account type.

How we measured

  • Lines: cloc 2.06 counted non-blank, non-comment lines in each app’s programming languages, for code that builds into the iPhone app. Characters were counted after removing comments and all whitespace. Excluded: tests; Android, desktop and web code; build tools; files marked as generated (protobuf, sqlc and UniFFI bindings); and vendored third-party code. Rust test modules inside source files were removed. Winnow’s test oracles, test vectors and UI tests are left out by name; Lean proofs are counted as lines.
  • Complexity: each file was parsed with tree-sitter, and one rule applied to every language. CC is 1, plus 1 for each if or guard, loop, catch, ternary, &&, ||, ?? or elvis, and non-default case, when or match arm. Closures, lambdas and nested functions count toward the function that contains them, so a React screen written as one function component counts as one function. Tree-sitter could not fully parse at most {{PE_MAX}}% of any wallet’s files; it recovers locally, so their functions are still counted. No tree-sitter grammar parses current Lean, so Lean is read lexically under the same rule: each def, instance, abbrev or opaque is a function, and theorems are not.
  • Dependencies: read from each app’s own lockfiles (Swift Package Manager, Lake, CocoaPods, npm, yarn and bun). Kotlin libraries were resolved from Maven Central’s metadata for the iPhone target. Rust crates come from cargo tree for aarch64-apple-ios at each prebuilt library’s pinned source. Go modules come from go list -deps for iOS, with the build tags LND’s own iOS build uses or, for Muun, none.
  • Vendored code: each repository was searched for third-party code committed into it: vendor directories, committed CocoaPods, copied npm packages, license files below the root, committed binaries and dependency patches.
  • Features: each cell was checked by hand in the app’s and the engine’s source {{REVIEWED}}, at the revisions in reviewed.json. The build compares every cited passage with today’s code and lists any that have changed. The rows and what each value means are in features/rows.json.
  • Embedded engines: counted at the version each app pins, as the named library only, and kept out of every total. Winnow’s LeanNative ({{LEANNATIVE_SRC}}) is the commit its lake-manifest.json pins: its Lean framework, the Lean that prints the shell’s Objective-C, and its C shim. Phoenix’s lightning-kmp comes from its Gradle catalog. Bitkit’s LDK Node and libraries come from its Package.resolved, and rust-lightning from LDK Node’s lockfile. Blixt’s LND is the fork its react-native-turbo-lnd release builds. Zeus’s LND, LDK Node and Cashu versions come from its fetch-libraries-versions.json, and its count uses its default embedded LND. Green’s gdk is the release its fetch_gdk_binaries.sh downloads.

Reproduce it

Everything on this page is generated from the source repository. It pins every project to an exact commit, and data.json holds every measurement, including the full package lists. To rebuild it:

git clone https://github.com/winnowwallet/compare
cd compare
npm ci && pip install -r requirements.txt
./build          # fetch the pinned sources, measure, render
git diff         # nothing changes if the measurement reproduces

It needs Python 3.11, Node, Go and Cargo, plus network access to GitHub, crates.io, the Go module proxy and Maven Central; no Lean toolchain is needed. Feature cells and profile facts are reviewed by hand. The build checks that every citation resolves at the revision it was reviewed against, and reports which cited code has changed since.

Not compared

This comparison needs the iPhone app’s source, so closed-source and custodial wallets cannot be measured and are left out, however widely they are used. Other open-source wallets could be added.
