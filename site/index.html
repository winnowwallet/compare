Winnow compare · Bitcoin on iPhone

Bitcoin wallets compared

How Winnow compares with seven other open-source iPhone wallets that hold your own Bitcoin keys: features, code size, complexity and what each one depends on. Everything is measured from source and rebuilt every day.

Winnow is a Bitcoin-only wallet written in Swift, with one third-party dependency. It counts 21,997 lines of its own code, 8,965 for the app and 13,032 for its Bitcoin library. It checks the chain on the phone with compact block filters from Bitcoin peers it finds itself, receives to Taproot addresses, and reaches Tor and I2P through gateways you run, with no client of its own. The other wallets count 1.7 to 8.6 times as many lines, without counting the node or wallet engines that most of them embed. What the comparison leaves out

Complexity and CRAP

CRAP scores each function by its cyclomatic complexity (CC, the number of paths through it) and how much of it the tests run: CRAP = CC² × (1 − coverage)³ + CC. Coverage needs each project’s test suite run with instrumentation, on a Mac for the Swift apps, so it is not measured here. Testing can only bring CRAP down to CC, so the complexity alone sets a floor: a function above 12 scores above 12 however well it is tested, and one above 30 fails crap4j’s default threshold whatever its tests. Complexity is measured on each wallet’s counted code, not on embedded engines.

1.5% of Winnow’s functions are above 12, against 0.8–8.0% for the others. Winnow’s most complex function scores 27. Its mean is 3.3; the others’ range from 1.9 to 5.3. Winnow’s CI also rejects any function over 8 as SwiftLint counts complexity, which leaves out case arms, &&, ||, ?? and ternaries; this page counts all of them, so its numbers are higher.

What the numbers leave out

Less code is not proof of safety

A smaller codebase is quicker to read and review. It does not show the code is correct, and it says nothing about whether anyone independent has reviewed it. Check each project’s own security page.

The wallets do different amounts of work

Each count is the whole app, not only its on-chain wallet. Zeus also manages remote LND and Core Lightning nodes and includes Cashu, Nostr Wallet Connect and a point of sale. Bitkit includes Pubky contacts, Paykit and Trezor support. Winnow includes shared accounts with MuSig2 and 2-of-3 signing. BlueWallet includes Lightning wallet types (an LNDHub custodian and an Ark one). Green’s count includes its lightning folder. Muun includes Lightning payments through swaps.

Engines are not counted

Phoenix, Bitkit, Blixt, Zeus and Green build their Bitcoin wallet on an engine that is a separate project: lightning-kmp, LDK Node with BDK, LND and gdk. The code size and complexity here are for the wallet itself, so those wallets look smaller than everything they ship. Winnow, Muun and BlueWallet have no such engine. Winnow and Muun keep their own Bitcoin library in the repository, which is counted.

Who can move on-chain funds

Where a service has to cosign, the wallet cannot spend without it, or only after a delay. The fourth column of the table at the top says which wallets that applies to, and the notes under each cell give the account type.

How we measured

  • Lines: cloc 2.06 counted non-blank, non-comment lines in each app’s programming languages, for code that builds into the iPhone app. Characters were counted after removing comments and all whitespace. Excluded: tests; Android, desktop and web code; build tools; files marked as generated (protobuf, sqlc and UniFFI bindings); and vendored third-party code. Rust test modules inside source files were removed.
  • Complexity: each file was parsed with tree-sitter, and one rule applied to every language. CC is 1, plus 1 for each if or guard, loop, catch, ternary, &&, ||, ?? or elvis, and non-default case, when or match arm. Closures, lambdas and nested functions count toward the function that contains them, so a React screen written as one function component counts as one function. Tree-sitter could not fully parse at most 5% of any wallet’s files; it recovers locally, so their functions are still counted.
  • Dependencies: read from each app’s own lockfiles (Swift Package Manager, CocoaPods, npm, yarn and bun). Kotlin libraries were resolved from Maven Central’s metadata for the iPhone target. Rust crates come from cargo tree for aarch64-apple-ios at each prebuilt library’s pinned source. Go modules come from go list -deps for iOS, with the build tags LND’s own iOS build uses or, for Muun, none.
  • Vendored code: each repository was searched for third-party code committed into it: vendor directories, committed CocoaPods, copied npm packages, license files below the root, committed binaries and dependency patches.
  • Features: each cell was checked by hand in the app’s and the engine’s source on 2 October 2026, at the revisions in reviewed.json. The build compares every cited passage with today’s code and lists any that have changed. The rows and what each value means are in features/rows.json.
  • Embedded engines: counted at the version each app pins, as the named library only, and kept out of every total. Phoenix’s lightning-kmp comes from its Gradle catalog. Bitkit’s LDK Node and libraries come from its Package.resolved, and rust-lightning from LDK Node’s lockfile. Blixt’s LND is the fork its react-native-turbo-lnd release builds. Zeus’s LND, LDK Node and Cashu versions come from its fetch-libraries-versions.json, and its count uses its default embedded LND. Green’s gdk is the release its fetch_gdk_binaries.sh downloads.

Reproduce it

Everything on this page is generated from the source repository. It pins every project to an exact commit, and data.json holds every measurement, including the full package lists. To rebuild it:

git clone https://github.com/winnowwallet/compare
cd compare
npm ci && pip install -r requirements.txt
./build          # fetch the pinned sources, measure, render
git diff         # nothing changes if the measurement reproduces

It needs Python 3.11, Node, Go and Cargo, plus network access to GitHub, crates.io, the Go module proxy and Maven Central. Feature cells and profile facts are reviewed by hand. The build checks that every citation resolves at the revision it was reviewed against, and reports which cited code has changed since.

Not compared

This comparison needs the iPhone app’s source, so closed-source and custodial wallets cannot be measured and are left out, however widely they are used. Other open-source wallets could be added.

  • Exodus, Cash App and Strike are widely used iPhone wallets whose apps are closed source, so there is no code to measure or cite.
  • Envoy, Bull Bitcoin, Bitcoin Keeper, Cake Wallet and Edge publish source code and may be added. Each needs a measured iPhone build and a hand review of its features.
